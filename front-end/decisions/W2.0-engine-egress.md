**Status: BUILT & BROWSER-VERIFIED (headless)** — written 2026-11-13, the session
after the P1 merge (#161). Closes the mobile-egress hole the PO's phone test found
(4–5 plays → the relay's datacenter egress throttled). This record documents the

### The model that fell out

* googlevideo authorizes cross-IP, cross-UA fetches — the URL is the ticket.
* But from datacenter IPs it serves **only ~1 MB per URL generation** (per video).
* The P1 relay playback worked because the chunkFetcher's `onStaleUrl` rotation
  re-resolved on 403s — each fresh URL bought another ~1 MB prefix. A 3.4 MB song
  cost ~4 player POSTs; 5 songs ≈ 20 POSTs in minutes → the aggregate that
  "banned" the relay. **The ban was the player API's resolve rate, not the media
  throttle itself.**
* The bare element (the only user-IP byte lane) sends open-ended ranges, which
  the prefix rule refuses outright — on datacenter IPs. **Whether residential /
  mobile 5G IPs serve open ranges is THE remaining unknown** — the PO's phone is
  the only instrument that can measure it (by construction: the sandbox has no
  residential egress).

## The architecture (shipped)

**DUAL-LANE element playback with automatic failover, driven by the wasm engine:**

```
                    ┌────────────────────────────────────────────┐
                    │  WasmEnginePort (W2.1, streamify-core)     │
                    │  queue · state machine · debounce · rev    │
                    └───────────────┬────────────────────────────┘
                                    │ PlayIntent (latched, at-least-once)
                    ┌───────────────▼────────────────────────────┐
                    │  ElementPlayer (dual-lane sink)            │
                    │  lane 1: DIRECT  <audio src=googlevideo>   │  ← user's IP,
                    │          (open ranges; residential?)        │    zero relay bytes
                    │  lane 2: BRIDGE  <audio src=/swgv/<token>> │  ← SW → relay →
                    │          (bounded 512 KiB via the SW)       │    googlevideo
                    └────────────────────────────────────────────┘
```

* **Lane 1 (direct)** is the mobile production lane: media bytes ride the user's
  own IP exactly like YouTube's own player. On open-range-refusing networks it
  fails fast (media error) and —
* **Lane 2 (bridge)** takes over automatically (per load) and flips the
  session-wide lane preference: the Service Worker serves same-origin
  `/swgv/<token>` URLs, translating the element's open range into a bounded
  512 KiB span fetched from the RELAY (CORS-open, readable — synthetic 206s
  with real Content-Range/Content-Type). Works on every IP class (E9c).
  URL rotations swap the upstream inside the worker — the element's src never
  changes.
* **`no-referrer` page policy** is load-bearing for lane 1 (E7).
* The resolver's `elementCompat` mode pins itag 140 (AAC) — universal element
  decode; the spine keeps its WebCodecs preference.
* The WASM spine (P1) remains the opt-in "engine path" (desktop quality mode,
  relay bytes, LUFS + underrun gate) behind the egress switch.

### What the bridge lane honestly costs

On datacenter networks the bridge inherits the ~1 MB prefix rule: mid-file
seeks beyond the prefix cannot be served (fresh URLs only buy head bytes), and
full-song playback rides the rotation machinery (a player POST per ~1 MB).
This is the SAME load profile P1 had — the bridge lane is the compatibility
fallback, not the mobile answer. **The mobile answer is lane 1**, whose
residential viability is the one open question (below).

## W2.1 — the engine facade (`crates/streamify-engine-wasm`)

The control plane mirrors the Android EnginePort / UDL `StreamifyEngine`
semantics on single-threaded wasm (streamify-core is std-only — W1.7-proven):

| UDL semantic | Web lowering |
|---|---|
| dispatch thread + coalesced pushes (MP-C02) | synchronous listener fire after every committed mutation; the JS event loop is the dispatcher |
| rev starts at 1, strictly monotonic; debounced commands bump nothing | identical (the TS wrapper keeps the Android `rev <= lastSeen` drop-guard) |
| 100 ms media-command debounce (`media_command_key`) | identical, clock = `js_sys::Date::now()` |
| one-way Idle→Buffering; Stop→Idle; transport never touches lifecycle; empty-queue transport = acknowledged no-op; Seek clamps; `play_track` needs a staged URL | identical — 17 wasm-bindgen tests in headless Chrome, all green |
| producer thread + PlayIntents | latched intent in the snapshot; the JS sink consumes + acks via `take_play_intent` |
| DAC clock ingest (8k–192k) | identical (element `currentTime` → frames @ 48 kHz) |

**Web extensions (documented):** `report_sink_state` (the element's
waiting/playing/pause mirror — the Android bridge's Media3 fusion, narrowing
only), `report_track_ended` (auto-advance, no wrap; queue exhausted → Idle),
`resolve` intents (async web resolver confirms via `stage_stream_url` +
`play_track`).

**The re-entrancy landmine (measured, fixed):** wasm-bindgen's borrow guard
throws `recursive use of an object detected` when the JS listener calls back
into the engine synchronously (the Rust side invokes the callback from inside
its own `&mut` borrow — `commit()` during `play_track`). The UDL engine has a
dedicated dispatch thread for exactly this reason; the web lowering defers
listener work to a **microtask** (`queueMicrotask`), releasing the borrow
first. Microtasks run in order, so snapshot ordering is preserved.

The data plane (producer thread, SPSC ring, `Instant` parking) cannot cross to
wasm — the TS mirrors (worklet ring, byte-exact 96-byte SinkStats wire, epoch
flush) remain the web data plane, driven by the engine's intents.

## The honest open question (the PO's phone is the instrument)

Whether **lane 1 (bare element, open ranges) works from residential / mobile
IPs** — the one measurement no sandbox can produce. If yes: mobile users ride
their own IP for every media byte, the relay serves ~1 tiny POST per play, and
the IP-ban class of failure is gone by construction. If no: the WEB+POT URLs
(the attested, browser-minted ones) are the next candidate for element
playback (they are minted FOR browser consumption), and the bridge lane keeps
everything playing meanwhile. **The first licensed play from the phone after
this deploy IS the experiment** — the egress chip in the player bar shows
which lane served each track.

# W0.5 — R-C spend decision (WS-W P0)

**Status: DECISION (provisional on residential canary rows)** — written by ENG-W1 at the close
of the P0 proof, from the evidence collected in W0.2/W0.4 plus the datacenter baseline measured
during the proof. Supabase `canary_results` rows are pending (the PO has the migration at
`front-end/canary/migrations/001_canary_results.sql` + recruits the residential testers — the
table does not exist yet, so every residential number below is structurally reasoned, not
measured; the doc is written so the canary data can only move the *revisit* clause, not the
recommendation).

## Recommendation: NO-SPEND on R-C in P2/P3

The "zero-relay-bytes endgame" (browser resolves and pulls media directly, relay only for API
metadata) should **not** receive engineering weeks in P2/P3. The relay stays a first-class part
of the web architecture. Rationale:

### The four R-C conditions, against what P0 actually proved

| # | Condition | P0 evidence | Verdict |
|---|-----------|-------------|---------|
| R1 | Licensed-content playback from residential IPs | **Dead from datacenter regardless of request fidelity**: the W0.4 matrix probed the licensed videos (`4NRXx6U8ABQ` + the top licensed search rows) with the exact working request shape (correct app UA via the relay's UA table, current client versions, live `sts`) — YouTube answers `LOGIN_REQUIRED "Sign in to confirm you're not a bot"` from this IP class. Standard content (`dQw4w9WgXcQ`) resolves and streams fine. Whether residential IPs pass licensed playback is exactly what the canary measures — but note that **even a YES on R1-residential does not deliver R-C**: it improves the *relay* path too. | Weak, and not R-C-specific |
| R2 | PO-token minting in the browser | **Structurally impossible on the web build**: PO minting requires the botguard JS engine; `rquickjs-sys` (QuickJS) does not compile to `wasm32-unknown-unknown` (no libc, no shipped bindings — the W0.1 finding, W0.2-confirmed against the published manifest: `rquickjs` is an *unconditional* dependency of rustypipe 0.11.4, so the web build compiles it OUT and rides the PO-free client ladder). Reviving this means porting QuickJS to wasm via Emscripten + a wasm-side botguard runtime — a research project, not 4 weeks. | **Dead** |
| R3 | ACAO on googlevideo CDN URLs | Not yet measured from any browser (canary R3 does this). Historically googlevideo serves no `Access-Control-Allow-Origin` on media edges. **This is the decisive one**: without ACAO, any JS-consumed media (Web Audio / MediaElementSource — i.e. the ENGINE's DSP path, the entire point of the web port running the same engine as the APK) cannot read cross-origin media bytes; only the bare `<audio>`-element path (no DSP, no Web Audio graph) tolerates a CORS-opaque media URL. | Likely dead for the DSP path |
| R4 | IP-pin tolerance | P0 evidence so far: URLs minted via the relay (datacenter egress) stream to the browser over the relay *and* direct curl range-probes from the same sandbox — consistent IP egress on both ends. The canary's R4 (resolve via relay, fetch bytes direct from the residential browser) measures the real thing. | Open, favorable so far |

### The structural argument (what makes this a decision, not a hedge)

1. **The kill criterion went our way — and it devalues R-C's payoff.** The relay streams HTTP 206
   byte-range responses with intact `Content-Range`/`Accept-Ranges` (measured: `bytes 0-1024/1300631`
   + a mid-file seek at offset 1048576, both 206, MP4 ftyp magic bytes on the payload). The
   "relay bytes cost" R-C was meant to eliminate is real but small; the relay is not a bottleneck.
2. **R2 is dead and R3 is likely dead for the path that matters.** R-C needs *both* to be alive to
   deliver its "zero relay media bytes" story. Spending 4+ weeks on an endgame whose two load-bearing
   conditions are structurally unavailable is a misallocation — the same weeks moved into the
   engine's wasm port (P1) buy the actual product.
3. **The relay is doing more than "dumb proxy" work already — and well.** The P0 relay proved it
   must: CORS 403 on innertube (verified), UA normalization for app clients (verified — the
   browser cannot set app UAs), `sec-fetch-*` fingerprint stripping (verified — YouTube
   soft-blocks browser-marker'd app requests), and 206-faithful media streaming. These are
   *features of the browser threat model*, not overhead to remove.

### What the canary data can still change

The residential rows (`canary_results`, once the PO applies the migration and 5+ testers run
`/canary.html`) can move exactly one clause: **if a majority of residential testers pass R1 AND
R3 shows ACAO on googlevideo for their sessions**, add a P2 spike (≤1 week, not 4) to measure
how much media traffic could bypass the relay on the `<audio>` path. The DSP path stays
relay-dependent regardless (R2/R3). That is the only revisit trigger — recorded here so the
decision is auditable against the data when it lands.

### Concrete P2/P3 consequences of NO-SPEND

* The relay graduates from "P0 minimal" to the W4.1 hardening plan (JWT, rate limits, kill
  switch) as a *product surface*, not a temporary scaffold.
* Bandwidth cost modeling (P2) assumes 100% of media bytes through the relay (free-tier Workers
  egress today; revisit only on measured cost pain, which the relay's own `X-Relay-Ms` +
  accounting can quantify).
* The engine's wasm port keeps the PO-free client ladder as the web playback strategy
  (mirroring the engine's existing iOS degradation) — no botguard work on the web platform.

# W0.5 — R-C Spend Decision

**Decision: NO-SPEND on R-C in P2/P3. The relay is the endgame, not a bridge.**

Owner: ENG-W1 (WS-W) · Status: decided, pending W0.1b residential confirmation
(see "Reopen criteria" — the decision flips only on measured evidence, not on
hope) · Evidence base: W0.2/W0.4 sandbox runs (datacenter) + canary page live
run + repo fleet evidence (`fleet-config.json`, `resolver-canary.yml` history).

---

## What R-C promised

"Zero-relay-bytes endgame": the browser resolves and fetches media DIRECTLY
from Google, the relay carries only (or nothing of) the metadata traffic.
Four conditions were listed as unknowns: residential IP behavior, PO-token
minting in-browser, ACAO on CDN URLs, and IP-pin tolerance.

## Condition-by-condition, with measurements

### 1. Residential IP — partially open (data pending), but not decisive

Fleet evidence and this spike both show **standard content resolves from
datacenter IPs** (W0.4: dQw4w9WgXcQ playability OK via ANDROID_VR, 4 direct
audio formats, 0 ciphered). **Licensed content is bot-walled from datacenter
IPs** (canary run from the build sandbox: 9/10 clients LOGIN_REQUIRED on
4NRXx6U8ABQ; `fleet-config.json` licensedProbe: "bot-gated (datacenter-IP
wall, environmental)"). The W0.1b testers will quantify the residential
delta. But residential IP quality changes *how often the ladder succeeds*,
not the structural questions below.

### 2. PO-token minting in-browser — fail on economics, independent of data

The PO-free ladder (ANDROID_VR / ANDROID / IOS) needs no tokens — that is
the whole reason it exists, and it is the fleet that survives the canary.
Minting PO tokens in a browser means executing YouTube's challenge JS from
an origin it does not trust, re-armed on their schedule. W0.2 additionally
killed the only in-process minter we have (rustypipe-botguard rides
QuickJS/deno — no wasm32). Spending 4+ weeks here buys resilience for a
client tier we do not use.

### 3. ACAO on CDN URLs — MEASURED ABSENT. This kills the premise.

The canary's RC-3 probe fetched a direct googlevideo URL with
`mode: 'cors'` from a real browser:

```
RC-3 · CDN ACAO: acao-absent-cors-blocked
  direct range fetch threw (TypeError: Failed to fetch) —
  the CDN did not deliver a CORS-clean response to the browser
```

`Access-Control-Allow-Origin` is a *response policy*, not an IP-reputation
knob; there is no reason to believe residential testers see different
headers. Without ACAO, a third-party origin (GitHub Pages) can NEVER read
googlevideo responses — so "browser fetches media bytes directly" is
structurally impossible no matter which IP the visitor has. Meanwhile the
same URL fetched **through the relay** streams perfectly (206 + Content-Range
passthrough, verified end-to-end and sustained 25 s+ of playback).

### 4. IP-pin tolerance — MEASURED FAILED (datacenter); moot given (3)

RC-4 direct `<audio>` playback of the IP-pinned URL errored (MediaError 4).
Residential *may* differ — but even a tolerant pin cannot rescue a fetch the
CORS policy already forbids reading. The only surviving variant would be
opaque media-element playback of pin-tolerant URLs, which (a) still can't be
metered/decoded by the app, and (b) leaves the *resolution* path on the
relay anyway, since youtubei.googleapis.com never grants ACAO to us either.

## The economics never justified it anyway

- Cloudflare Workers bills **requests, not egress bytes**. Media through the
  relay costs the same as metadata: free tier = 100k req/day. A 3-minute
  track at 256 KiB bounded ranges ≈ 60 requests; the free tier covers
  ~1,600 full-track plays/day with zero budget. R-C's "savings" are
  therefore ~$0 at every scale P2/P3 contemplates.
- The relay already passes the kill criterion with margin: 206 partial
  content streams to browser-side fetch; 25+ seconds of Web Audio non-zero
  output measured in headless Chrome (peaks 0.41-0.60), console clean.
- The one real CDN behavior we must engineer around — burst throttling of
  rapid sequential ranges on one URL (~768 KiB burst window observed) — is a
  P1 pump-pacing/backoff/re-resolve tuning item inside the existing
  architecture, not an argument for changing architecture.

## Recommendation

**P2/P3 spend: zero.** The relay gets hardened in P4 (W4.1: JWT, rate
limits, kill switch) and stays. Engineering time that was pencilled for R-C
goes to the P1 pump (pacing, re-resolve, gapless queueing) and to the
engine change request from W0.2 (lift `json.rs` into a shared transport-free
crate) — both of which pay off on every platform, not just the web.

## Reopen criteria (explicit, data-driven)

Revisit ONLY if the W0.1b `canary_results` table shows, across ≥5 residential
testers:

- RC-3 `acao-present` in ≥30% of runs (contradicts every measurement so
  far), AND
- RC-4 `direct-play-ok` in ≥30% of runs.

Until both numbers exist, this decision is closed.

## Where the confirmation data lands

`public.canary_results` (migration: `front-end/canary/migrations/
001_canary_results.sql`): one row per probe run; `rc_conditions` jsonb
carries the RC-1..RC-4 verdicts verbatim. PO review query after tester
recruitment:

```sql
select rc_conditions->>'rc3_cdn_acao'  as rc3,
       rc_conditions->>'rc4_ip_pin'    as rc4,
       count(*)                        as runs
from canary_results
group by 1, 2;
```

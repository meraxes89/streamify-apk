# W0.2 Spike — rustypipe → wasm32-unknown-unknown

**Date:** WS-W P0 · **Branch:** `ws-w/p0-proof` · **Outcome: KILLED (for rustypipe 0.11.4 as published). P0 chain survives via the engine's pure parsing core — see "Pivot" below.**

## What was attempted (exactly as briefed)

`front-end/crates/streamify-wasm` with:

```toml
rustypipe = { version = "0.11.4", default-features = false }
```

Commands run (sandbox: rustc 1.99.1 stable, wasm32-unknown-unknown target installed):

```
cargo tree  --target wasm32-unknown-unknown -p streamify-wasm
cargo build --target wasm32-unknown-unknown -p streamify-wasm
```

## Finding 1 — rquickjs-sys is an UNCONDITIONAL dependency

The kickoff brief's W0.1 attribution ("QuickJS rides with the optional
rustypipe-botguard companion; default-features=false excludes it") is wrong in
detail. rustypipe **0.11.4**'s published manifest has exactly these features:

```
default = ["default-tls"]
default-tls / native-tls / native-tls-alpn / native-tls-vendored
rss / rustls-tls-native-roots / rustls-tls-webpki-roots / userdata
```

…and a plain, non-optional, non-target-gated dependency:

```toml
[dependencies.rquickjs]
version = "0.9.0"
```

QuickJS is rustypipe's **own embedded deobfuscation engine** (signature/n-cipher
transforms) — the repo already knows this: `rust/crates/streamify-resolver/Cargo.toml`
target-gates `rquickjs-sys = { features = ["bindgen"] }` for android/ios precisely
because there is no way to turn it off. `default-features = false` only removes the
TLS backend (the engine uses it for exactly that: keeping openssl-sys out of
cross-compiles).

`cargo tree --target wasm32-unknown-unknown` confirms — **rquickjs-sys v0.9.0 is in
the wasm32 graph** (3 occurrences):

```
├── reqwest v0.12.28
├── rquickjs v0.9.0
│   └── rquickjs-core v0.9.0
│       └── rquickjs-sys v0.9.0
├── tokio v1.54.1
├── localzone v0.3.1
```

## Finding 2 — the exact build failure

`cargo build --target wasm32-unknown-unknown` fails at the rquickjs-sys build
script (verbatim):

```
cargo:warning=rquickjs probably doesn't ship bindings for platform
  `wasm32-unknown-unknown(n/a)`. try the `bindgen` feature instead.
cargo:warning=Compiler family detection failed due to error:
  ToolNotFound: failed to find tool "clang": No such file or directory

error: failed to run custom build command for `rquickjs-sys v0.9.0`
  process didn't exit successfully: `.../build-script-build` (exit status: 1)

error occurred in cc-rs: failed to find tool "clang":
  No such file or directory (os error 2)
```

## Analysis — why this is a kill, not a work-around

Even granting clang + the `bindgen` feature (the repo's own android/ios
mitigation), compiling QuickJS's C sources requires a **libc and sysroot** for the
target. `wasm32-unknown-unknown` has **neither** — that is the whole point of the
target. The repo's android/ios bindgen dance works because Android SDK and iOS
simulator sysroots exist. On wasm32-unknown-unknown the bindgen route degrades
into vendoring a libc shim for QuickJS — a research project, not a spike.

Downstream of QuickJS, the rest of rustypipe's graph is also native-shaped for
this target: `tokio` with `["macros", "time", "process"]` (process spawning does
not exist on wasm32-unknown-unknown) and a reqwest configured without the wasm
`js`/fetch backend. These are all secondary to the rquickjs-sys kill.

Options that remain (all outside P0 scope):

1. **Upstream feature request** to rustypipe: make the QuickJS deobf engine an
   optional feature (or target-gate it). Without it, no rustypipe release ever
   compiles to wasm32-unknown-unknown.
2. **wasm32-wasip1**: WASI provides a libc, so QuickJS becomes plausible; but the
   browser then needs a WASI shim runtime to execute the module — a materially
   different architecture. This is the "bigger conversation" the kickoff flagged.
3. **Vendor a JS engine substitute**: use the browser's own JS engine for cipher
   work via wasm-bindgen instead of QuickJS. Only relevant for WEB-client
   signatureCipher URLs; the PO-free fleet ladder (ANDROID_VR / ANDROID / IOS)
   returns direct URLs and needs no deciphering at all.

## Pivot — why P0 does NOT stop here

Two facts from the engine itself make full-rustypipe-in-browser unnecessary for
the P0 proof:

1. **The engine's own production path doesn't use rustypipe for the fleet
   ladder.** Tier-5 anonymous extraction (`resolver.rs`) hand-posts the innertube
   player request (ANDROID_VR 1.65.10) and parses the response with the
   **pure** `InnertubeParser` (`rust/crates/streamify-resolver/src/json.rs` —
   serde_json only, zero HTTP, zero QuickJS, zero tokio). The same holds for
   legacy WEB_REMIX search. rustypipe's ladder (Desktop→iOS→TV) is a separate,
   higher tier — behind the PO-free clients this port rides.
2. **Even a hypothetically-compiling rustypipe would be unusable in-browser as a
   transport.** Its reqwest client would emit fetches to youtubei.googleapis.com
   from the page origin — CORS-blocked. The relay is structurally mandatory
   regardless (as the kickoff itself states). rustypipe's value in the browser
   reduces to its model types and parsers — and the engine already has
   production-proven parsing of the exact responses we need, in pure Rust.

Therefore `streamify-wasm` vendors `json.rs` **verbatim** (provenance header, no
edits) as `src/innertube.rs`, plus the client recipes from `resolver.rs`,
`tools/probe-clients.sh`, `tools/probe-search-resolver.sh` and
`fleet-config.json`. The web port executes the same extraction logic the engine
does — the difference is transport (browser fetch → relay instead of reqwest).

**P1 engine change request (for PO):** lift `json.rs` into a shared,
transport-free crate both `rust/` and `front-end/` workspaces can depend on, so
the vendored copy disappears and the parse core has one owner. Until then the
vendored file must be re-synced if the engine's parser changes.

## G0.1 disposition

- "rustypipe compiles to wasm32-unknown-unknown without rquickjs-sys in the
  tree" — **FALSE for rustypipe 0.11.4**, structurally (no feature can remove
  rquickjs). Spike evidence above; log: `rquickjs-sys` build-script failure.
- P0's three actual unknowns survive: (1) extraction logic compiles to
  wasm32 — **proven** via the vendored engine parser (`cargo build` green, wasm-pack
  pkg builds); (2) TS can call the engine — `ping()` proof; (3) browser plays
  audio through a relay without SharedArrayBuffer — W0.4.

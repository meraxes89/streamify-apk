# W1.0 — The minting surface: browser-native BotGuard PO tokens (WS-W P1)

**Status: BUILT & MEASURED** — written 2026-11-12, same session as the W1.1–W1.6 spine commit.
Closes the licensed-music hole the P0 canary found (`4NRXx6U8ABQ` → `LOGIN_REQUIRED` bot wall
from datacenter IPs for every innertube client). This record documents the architecture that
was locked, the experiments that eliminated every unlock hypothesis except environment trust,
and the one step that remains PO-side (redeploy the relay).

## The architecture (locked)

All minting traffic is **same-origin through the relay** — the page never talks to YouTube or
Google directly on the mint legs:

```
browser ──GET /bg-session────────────────────▶ relay ──▶ youtube.com homepage
                (visitorData + ytcfg + ytAtN challenge, server-cached 1 h)
browser ──GET /r?u=…www.google.com/js/th/…───▶ relay ──▶ BotGuard interpreter JS
browser ──POST /r?u=…jnn-pa…/GenerateIT──────▶ relay ──▶ WAA integrity token
browser   (locally: VM → snapshot → WebPoMinter → per-video PO token)
browser ──POST /r?u=…/youtubei/v1/player─────▶ relay ──▶ formats  (poToken injected
                                                           client-side in the body)
```

Three reasons, all measured:

1. **The WAA request key is origin-restricted.** `jnn-pa.googleapis.com` echoes any Origin in
   ACAO, but the GenerateIT request key is only valid for requests **without a foreign
   Origin**. Browsers force `Origin` onto every cross-origin fetch; the relay strips it
   (REQUEST_DROP) — upstream sees an origin-less request, byte-for-byte like the proven Node
   mint. Direct-to-jnn-pa from the page is therefore impossible, not merely impolite.
2. **One consistent egress IP.** POTs are IP-bound (the bgutil provider's own code comment).
   Mint and use must egress identically — with everything relayed, they do by construction.
3. **No CORS anywhere** — the page only ever fetches its own origin (the relay), and the
   mint's UA (the browser's own) is forwarded so the challenge/session pair stays coherent.

PO-token **injection is client-side by design**: the web resolver builds
`serviceIntegrityDimensions.poToken` + `X-Goog-Visitor-Id` and POSTs through `/r` — works
unchanged against the already-deployed P0 relay (verified: the P0 relay forwards both
verbatim), keeps the worker dumb.

### Binding rules (the fix that mattered)

yt-dlp's `pot/utils.py get_webpo_content_binding` is the ground truth, verified against the
live homepage (2026-11-12):

| Context | content binding | Why |
|---|---|---|
| player request (`serviceIntegrityDimensions.poToken`) | **VIDEO_ID** | PLAYER-context tokens are per-video |
| googlevideo `&pot=` (GVS) | **VIDEO_ID** while the homepage's `html5_generate_content_po_token` experiment flag is set (it is), else visitorData | the experiment rebinds GVS |

The first session's mints bound everything to visitorData — mechanically valid tokens,
wrong binding for the player request. `mintCore.gvsBindsToVideoId()` parses the flag from
the SAME ytcfg the mint consumed.

## The experiment matrix (what eliminated every hypothesis except environment trust)

All run 2026-11-12 from the dev sandbox against `4NRXx6U8ABQ`, provider-recipe Node mints
(pot-lab, bgutils-js 4.0.3, homepage ytAtN challenge incl. the 2026-08 patch):

| # | Hypothesis | Experiment | Result |
|---|---|---|---|
| 1 | token simply stale | fresh mint → immediate use | wall stays |
| 2 | wrong client | no-token matrix: WEB / MWEB / WEB_REMIX / WEB_EMBEDDED / TVHTML5 / TV_SIMPLY (direct) | all `LOGIN_REQUIRED` (or client dead) |
| 3 | wrong client for token | WEB+pot / MWEB+pot / WEB_REMIX+pot / ANDROID_VR+pot | wall stays |
| 4 | IP mismatch (mint IP ≠ use IP) | same-IP use (direct), and use via the live relay's CF egress | wall stays both ways |
| 5 | wrong binding | **video-id-bound** player token (correct per yt-dlp), direct + via relay | wall stays |
| 6 | environment trust | headless Chrome in-page mint (agent-browser, new headless) | **BotGuard VM refuses to score the environment** (`webPoSignalOutput` empty) — the designed `vm-score` failure path |
| — | sanity control | `dQw4w9WgXcQ` via ANDROID_VR, direct + via live relay + via local relay | `OK`, formats served, full playback |

Conclusions, in order of elimination: binding ✓ fixed, IP consistency ✓ controlled, client ✓
swept, freshness ✓ controlled. **The remaining differentiator is the mint environment**: the
BotGuard VM scores the environment (canvas/webgl/hardware entropy), and JSDOM (Node) mints
mechanically-valid but low-trust tokens that do not lift the wall, while headless Chrome is
refused outright. The unlock thesis is that a **real residential browser** — the production
user — mints a high-trust token that lifts it. That is exactly what the browser-native stack
delivers; it cannot be demonstrated from this sandbox (no real hardware, datacenter IP), and
the seed path below proves the wiring independently of that open question.

## Verified (browser, agent-browser headless Chrome + local `wrangler dev` relay)

- **Mint mechanics, browser**: `/bg-session` 200 (cache hit on second call), challenge
  descramble (`trayride`, ~39 KB program), interpreter ~64 KB via `/r`, VM loaded in-page,
  BotGuard snapshot executed → failed at the designed `vm-score` gate (headless). Every
  phase surfaced live in the UI.
- **Mint mechanics, Node through the relay** (mintCore's exact flow): full pipeline →
  integrity token (ttl 43200 s) → video-id-bound player+GVS tokens. `RELAY MINT PLUMBING: OK`.
- **Hop protocol, browser-fidelity**: googlevideo probe → `200 + X-Relay-Status: 302 +
  X-Relay-Location: <edge url>` → edge URL serves `206` directly; 64 KiB chunk lands with
  EBML magic bytes.
- **Licensed rung, seeded** (video-scoped dev token from the Node mint): both rungs execute
  and report — `[ANDROID_VR] LOGIN_REQUIRED · [WEB+POT] LOGIN_REQUIRED` — the seeded token
  rides `serviceIntegrityDimensions` through the relay; the wall's refusal is surfaced
  verbatim (the environment-trust question, not a wiring gap).
- **Standard track regression**: `dQw4w9WgXcQ` through the NEW resolver + hop protocol →
  Playing, 2378 packets demuxed/decoded, **0 underruns, G1 gate PASS**, and the relay log
  shows `403 → re-resolve → 200` (the `onStaleUrl` rotation surviving the datacenter-IP
  range throttling).

## The one pending PO step

**Redeploy the relay** (`cd front-end/relay && npx wrangler deploy` — credentials over a
secure channel, used once, never in the tree; see the relay README's *Deploy*). The LIVE
worker still runs the P0 code: it has no `/bg-session`, refuses `www.google.com` and
`jnn-pa.googleapis.com` (the web app detects exactly this and shows the relay-too-old
notice), and follows redirects server-side (the hop protocol degrades gracefully to it).
Until the redeploy, production pages can resolve and play standard tracks through the live
relay but cannot mint.

## Honest open question

Whether a real-browser, residential-IP mint lifts the licensed wall — by construction the
sandbox cannot answer it (no real hardware; datacenter egress). Everything up to that
gate is proven: the mint runs natively in the page, all legs egress consistently through
the relay, the binding follows yt-dlp's ground truth, and the pipeline plays unlocked
content end-to-end. The production user's first licensed play is the experiment.
